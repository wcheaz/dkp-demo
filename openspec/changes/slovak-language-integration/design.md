## Context

The application is a Next.js 16 single-page app with a CopilotKit chat sidebar and a design gallery. All user-facing strings are hardcoded English across 5 frontend files (~100 strings). The Python backend (PydanticAI agent) has a static English system prompt.

The target audience is Slovak-speaking construction professionals. The developer does not speak Slovak and needs English as the development default. The app has one route, no SEO requirement, and deeply integrates CopilotKit into the page — making route-based locale switching impractical.

## Goals / Non-Goals

**Goals:**
- Every user-facing string flows through a translation dictionary keyed by locale.
- Slovak is the default in production builds; English is the default in development.
- Developer can toggle between languages in development for parity checks.
- Agent responds in the language matching the frontend's current locale.
- Translation key parity between `en.json` and `sk.json` is enforced by a script.

**Non-Goals:**
- Route-based locale switching (`/sk/`, `/en/`).
- Server-side locale negotiation or SEO.
- Translating LLM-facing tool names, descriptions, or parameter docs.
- Translating deployment scripts, CI configs, or developer comments.
- Currency conversion — the pricing formula remains unchanged; only display formatting changes.
- Supporting more than two locales.

## Decisions

### D1: Use `next-intl` with client-side locale switching (no route segments)

**Choice**: `next-intl` configured for client-side locale switching via a React context, not via `[locale]` route segments.

**Rationale**: The app is a single `page.tsx` with CopilotKit deeply woven in. Route segments would require re-initializing the CopilotKit provider and add complexity with no benefit (no SEO, single page, no public users).

**Alternative considered**: `next-i18next` with route segments — rejected because it adds routing complexity for a single-page app and would interfere with CopilotKit provider initialization.

**Alternative considered**: `react-intl` without Next.js integration — rejected because `next-intl` provides better App Router integration, `useTranslations()` hook, and built-in TypeScript support.

### D2: Language toggle is dev-only, hidden in production

**Choice**: A `LanguageToggle` component that conditionally renders based on `process.env.NODE_ENV`. Returns `null` in production.

**Rationale**: End users only know Slovak — a toggle would confuse them. The toggle exists solely for the developer to verify Slovak rendering parity. In production builds (`NODE_ENV=production`), the component tree does not include the toggle at all.

### D3: Environment-based default locale

**Choice**: `NODE_ENV=development` → default locale `en`. `NODE_ENV=production` → default locale `sk`. The default is set via a `data-default-locale` attribute on `<html>` at build time, read by the client-side `LanguageProvider`.

**Rationale**: The developer works in English for comprehension. Slovak users see Slovak immediately. The `localStorage` preference overrides the default, so the developer's toggle choice persists across sessions.

**Config shape**:
```typescript
// src/i18n/config.ts
export const locales = ['sk', 'en'] as const;
export type Locale = (typeof locales)[number];
// default determined by NODE_ENV, baked into HTML attribute at build/render time
```

### D4: Translation dictionary structure — flat keys by component/section

**Choice**: Nested JSON keyed by component/section (e.g., `sidebar.title`, `designs.heading`, `pricing.totalCZK`).

**Rationale**: Grouping by component makes it easy to find related strings and verify completeness per component. The `next-intl` `useTranslations('section')` hook naturally scopes to a namespace.

**Key structure**:
```
sidebar.title, sidebar.placeholder, sidebar.greeting, sidebar.suggestions.*
designs.heading, designs.empty, designs.materialEstimate, designs.price, designs.generating, designs.labels.*, designs.params.*
pricing.title, pricing.floorArea, pricing.joints, ..., pricing.error, pricing.storedPrice, pricing.exclVAT
alerts.fileTooLarge, alerts.uploadLimit, alerts.csvParseError, alerts.excelParseError
metadata.title, metadata.description
```

**Rule**: `en.json` and `sk.json` MUST have identical key structures. The parity check script enforces this.

### D5: Agent locale passed dynamically, not hardcoded

**Choice**: The system prompt is generated by a function `get_system_prompt(locale: str) -> str` that appends a language instruction based on locale. The frontend passes its current locale to the agent via CopilotKit context.

**Rationale**: Hardcoding "respond in Slovak" would cause the agent to produce awkward mixed-language output when the developer sends English prompts during testing. Dynamic locale adaptation means the agent responds in English during dev and Slovak in production.

**Agent prompt shape**:
```python
def get_system_prompt(locale: str = "sk") -> str:
    base = "<existing system prompt unchanged>"
    language_instruction = {
        "sk": "\n\nIMPORTANT: Respond in Slovak (Slovenčina). All user-facing text must be in Slovak.",
        "en": "\n\nRespond in English.",
    }
    return base + language_instruction.get(locale, language_instruction["sk"])
```

### D6: Tool descriptions stay in English

**Choice**: CopilotKit tool names, parameter descriptions, and tool descriptions in `page.tsx` remain English. Only user-visible sidebar labels, suggestion text, and UI strings are translated.

**Rationale**: Tool descriptions are LLM-internal instructions. English tool descriptions work correctly regardless of the agent's response language. Translating them would add maintenance burden with no user benefit.

### D7: Number/currency formatting uses `Intl.NumberFormat` with `sk-SK` locale

**Choice**: Replace all `toLocaleString("en-US")` calls with `Intl.NumberFormat('sk-SK', ...)` for display formatting. The pricing formula (CZK, GBP) remains unchanged — only the display format changes.

**Rationale**: Slovak locale uses space as thousands separator, comma as decimal separator, and `Kč` suffix for CZK. This matches end-user expectations.

### D8: Parity check script as CI gate

**Choice**: `scripts/check-i18n-parity.mjs` compares flattened keys between `en.json` and `sk.json`. Missing keys = exit 1. Added to `package.json` as `i18n:check` script.

**Rationale**: Key drift between dictionaries is the most common i18n bug. A deterministic script catches it before deployment. JSON format is used because models are less likely to casually rewrite JSON than markdown.

## Risks / Trade-offs

**[Risk] Slovak text is 15-30% longer than English** → Mitigation: UI containers use flexible sizing (`overflow`, `text-wrap`, `min-width`). The parity check includes a visual checklist for overflow in both languages.

**[Risk] Translation quality depends on non-native translations** → Mitigation: Domain terminology (väzník, pôdorys, rímsa, etc.) comes from original Slovak documents and is reliable. General UI strings are based on the planning doc's translations. A native speaker review is documented as a human handoff item, not a loop task.

**[Risk] CopilotKit context forwarding may require agent-side changes** → Mitigation: The locale is passed as metadata through CopilotKit's existing context mechanism. The agent reads it from `RunContext[StateDeps]` which already exists. If the context path is unclear, the fallback is a query parameter on the API route.

**[Risk] `next-intl` server config may conflict with App Router defaults** → Mitigation: Using client-side `LanguageProvider` context instead of `next-intl`'s server-side `getRequestConfig` avoids middleware and route segment complexity. The server config is minimal — just message loading.

**[Trade-off] Dev-only toggle means production Slovak rendering is only verified by visual inspection in dev mode** → Accepted: The developer toggles to Slovak in dev, verifies structure (no missing keys, no overflow), then ships. Content accuracy is a separate human handoff.

## Human Handoff

The following items require human action outside the autonomous loop:

1. **Native Slovak speaker review** — Review all Slovak translations in `sk.json` for natural phrasing and correct domain terminology. The developer cannot judge translation quality.
2. **Agent Slovak response quality** — Review a sample of agent Slovak responses for grammatical correctness and natural construction terminology.
3. **Slovak knowledge base** — Consider creating a Slovak knowledge base directory (`knowledge/trusses-ai-slovak`) if Slovak-language source documents should be used directly. Currently only `trusses-ai-english` exists.

## Migration Plan

1. Install `next-intl` — zero breaking changes, purely additive.
2. Create i18n infrastructure files — no existing code touched yet.
3. Migrate one component at a time, starting with the largest (`page.tsx`), then `design-component.tsx`, `pricing-breakdown-modal.tsx`, `add-design-button.tsx`, `layout.tsx`.
4. Add agent locale awareness — backwards compatible, English still works.
5. Add parity check script to CI.
6. No rollback needed — each step is additive. Removing the i18n layer reverts to hardcoded strings.
